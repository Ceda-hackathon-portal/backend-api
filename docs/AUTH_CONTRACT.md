# Phase 4B Cognito/session contract

Local implementation authorized by owner: "proceed to 4B" after Cognito Lite recommendation. This approves provider-specific code, NOT AWS user-pool creation, paid services, deployment or frontend changes. Auth is disabled by default. No live Cognito pool/contact used during tests. This document retains the Cognito implementation and adds an explicitly selected local-development mode. Local mode is only available with `NODE_ENV=development`, `AUTH_MODE=local`, and a loopback `HOST` (127.0.0.1, ::1, or localhost). Both configured origins must also be loopback HTTP origins. It uses a configured local email and an scrypt password hash generated by `npm run auth:hash-local-password`; do not use a shared or production credential. It uses the same PostgreSQL-backed opaque sessions, HttpOnly development cookies, CSRF token binding, logout revocation and session verifier. Local identities receive no seeded roles or grants. It does not call Cognito, and `/login` and `/callback` are available only in Cognito mode. Local mode fails startup outside development or if the listener/origins are not loopback.

Local endpoint: `POST /api/v1/auth/local-login` accepts `{ "email": string, "password": string }`. It requires the exact configured Origin, the anonymous cookie and `X-CSRF-Token` returned from `GET /csrf`. Invalid credentials return the generic `401 LOGIN_FAILED`; success returns `{data:{authenticated:true}}` and sets the same opaque session cookie used by `GET /session`. The password is never stored in PostgreSQL or returned. There is no local registration, password reset, user selection, or staff grant provisioning.

The legacy statement that local password login is unimplemented is superseded by this local-only endpoint. No local mode is enabled by default.

In Cognito mode, auth paths are mounted only with AUTH_ENABLED=true; otherwise they return404. In local mode, only local-login, csrf, session and logout are mounted. Every response uses no-store. Session/grants authorization remains separate from Cognito. The API never accepts a Cognito token as an application bearer session. No provider refresh/access/ID token returned to browser or persisted.

Common errors400 malformed JSON,413 size,415 encoding/type,422 DTO,429 limiter,500 sanitized store/runtime failure. Callback authentication failures are intentionally generic401 (including failures during callback account/session creation); no provider error text/stack exposed. Error envelope unchanged: {error:{code,message,requestId,details?}}. Existing body limit64KiB/CORS/headers remain. No ETag/private HTTP cache.

Browser flow for frontend owner (no frontend edits): fetch /csrf with credentials; POST /login with credentials, exact Origin and returned X-CSRF-Token; navigate to authorizationUrl. The fixed callback sets cookie and redirects to workspace. Restore using /session; fetch a current /csrf before POST logout. Keep CSRF/private queries only in account-scoped memory, clear/cancel on logout/account switch/401. No localStorage tokens. Cognito hosted UI supplies account registration/recovery; API does not handle passwords. Old credential-login form contract is explicitly replaced, not silently mapped.

Current mismatch: roles/grants persistence and assignment adapters are not implemented; newly mapped identities deliberately receive []/null, not synthetic staff or applicant privileges. authzRevision is not returned until grant persistence defines it. Current frontend assumes user.role is a string; owner must handle no-grant/loading states before integration. Six application fields unchanged, business endpoints still unavailable. The earlier generic Session DTO is a target pending grants, not the current auth response. No /me profile mutation yet.

Logout revokes only the backend session, not Cognito's hosted SSO cookie. Login currently uses prompt=login to request reauthentication; test its exact Lite hosted-UI behavior against the chosen pool before any real demo. Never claim Cognito global signout/account disable instantly revokes local sessions: local user suspension and session revocation must be coordinated administratively; no administration endpoint exists yet. No MFA assurance is inferred from OIDC; authnLevel='oidc' is not MFA proof. Staff access stays unavailable pending MFA/onboarding/grant policies.

Cookies: production/HTTPS __Host-ceda_session, __Host-ceda_oidc, __Host-ceda_csrf; Secure,HttpOnly,SameSite=Lax,Path=/,no Domain. Explicit loopback-only HTTP development uses dev_ names without Secure; never deploy that mode. Session Max-Age8h default but database idle30m/absolute8h are authoritative/configurable. Duplicate/malformed token cookies rejected. Callback URLs/Origin built from validated configured origins, not request Host/forwarded headers.

Use the SAME hostname for local API and frontend (for example localhost:3001 and localhost:5173). Mixing localhost and127.0.0.1 makes them different sites and SameSite=Lax will prevent expected credentialed fetch behavior. Production likewise needs same-site origins or an approved revised cookie/CSRF design; CORS alone does not solve cross-site cookie restrictions.

Server verifier exported by authRoutes adapts durable sessions to Phase4A Principal. No business route is connected to it yet; ScopedAuthorization still needs a real grant/resource reader and transaction-bound rechecks. No authorization decisions are cached. Login/callback limiter is bounded per-process20 requests/IP/minute,10000 tracked IPs; it is not durable/distributed or a replacement for deployment abuse controls. Deployment must prove proxy trust and limiter behavior.

### Account suspension

Suspension revokes every existing backend session for that account in the same PostgreSQL transaction. Reactivation requires a fresh sign-in. Migration 202611180001_suspend_sessions also revokes outstanding sessions for accounts suspended when the migration runs. Historical suspensions of currently active accounts cannot be identified from the current status alone.

## Application integration update

Application routes and persistent scoped grants are now implemented as documented in API_CONTRACT.md. The session endpoint still returns empty capability/role arrays until a reviewed capability projection is added. That DTO is not an authorization decision. The API verifies current sessions and the application repository checks ownership inside each transaction. Staff transaction consumers call requireProgrammePermission against live grants. Hosted Cognito verification remains synthetic in local tests; production browser/provider acceptance remains outstanding.
