# Runtime role and application API verification

The API uses existing Cognito/session and CSRF mechanisms. No application bearer tokens or client-selected roles are introduced.

ops/runtime-role.sql is a reviewed provisioning candidate for a migration-owner session after migrations. It creates a NOLOGIN permission group. Provision a separate nonsuperuser LOGIN with externally supplied secret and membership in that group; use that URL for runtime only. Never grant membership in the owner/migration role. Apply the database-level PUBLIC CREATE/TEMP revocations only after reviewing effects on existing users. The script is intended for one-time provisioning, not app startup.

Permissions:
- SELECT on needed auth and domain tables; INSERT on auth mapping/session and application command tables.
- Auth/session UPDATE, expired-attempt DELETE and column-limited application/outbox UPDATE.
- UPDATE(id) on users and programme_grants supports PostgreSQL row locks. Additive runtime_guards migration prevents changing those IDs or grant identity fields.
- No programme/config/grant insertion by runtime. Staff provisioning and programme setup use separately reviewed privileged tooling.
- No ownership, DDL, CREATE/TEMP, TRUNCATE, replication settings, role escalation or Prisma migration-table privileges.
- UUIDs are generated by application code; no sequence permissions required.
- A shared service role can SELECT database records to perform authorized application queries. Tenant isolation is enforced by authenticated repository filtering and HTTP DTOs; this slice does not implement per-applicant database RLS.

Disposable tests create a separate LOGIN with a random password and a scoped SCRAM pg_hba rule. Wrong-password connection is rejected. The actual restricted connection runs auth mapping/session creation, HTTP draft/submit and immutable reads. Tests deny disabling triggers, ALTER/DROP/TRUNCATE, replication mode, CREATE/TEMP, owner-role escalation, migration-table insertion/read and immutable-record mutation. They verify the role is not a member of the table owner. Correct HTTP lifecycle, cross-owner hiding, programme mismatch, stale revisions, CSRF, invalid input, concurrent receipts, request UUID correlation, HTTP audit/outbox rollback, expiry/revocation/suspension and restart persistence are exercised.

No shared environment has been configured. Target role membership, PUBLIC privileges, existing object ownership, backups and SQL must be approved before shared migration. Test fixture owner credentials are used only for setup, fixture identities/configuration and scoped fault triggers. Production operations use the restricted client.

Developer B can consume ApplicationService.readSubmission with authorized principal/application/version, transaction.programme for the pinned published configuration, transaction.requireProgrammePermission for exact capability scope, and transaction.record for A-owned application revision audit/outbox. Read and write adapters for the generic eligibility port still require B's approved policy types and eligibility/review schema. Do not use application.record to invent extra workflow audit revisions; B workflow history will be separate.

Reviewable application PR is based on canonical 9af1779. It includes the additive application and runtime guard migrations, service/repository/routes, role setup, tests and implemented API docs. Foundation and team-documentation candidates remain separate. Historical migrations and B modules remain unchanged. No remote publication is authorized.
