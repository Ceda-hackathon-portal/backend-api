# Frontend field inventory and explicit mapping

Snapshot: 2026-11-09. Sources are relative to src/: portal.js is data/portal.js; contexts live in context/; named pages in pages/; shared components in components/shared/. Inspected requested pages plus AuthPage, DashboardPage, ChallengesPage, SearchPage, InformationPage, SystemPage, main/App, useAuth, portal utilities, shared components and asset loading. Rows grouping presentation-only state explicitly have no database persistence. Loop aliases, event objects and callbacks do not introduce business fields.

All rows are design mappings, not implemented DTOs. Private HTTP responses always use Cache-Control: no-store. Snapshot fields freeze at submit; a requested revision edits a separate draft. Empty draft values map to NULL and serialize back as empty strings. SQL uses character bounds; API repeats JS UTF-16 limits to match HTML, including emoji boundary tests. Case-normalized email policy remains provider-reviewed; password contents are never trimmed.

## Mismatches requiring frontend-owner work (never edit frontend here)

1. Authentication is self-selected demo identity; add session-loading/expiry states after provider approval. user.role is UI selection, not sole authority.
2. localStorage shares records across roles; no automatic migration. Live private query caches must be memory-only, per user/session generation, and cleared on switch/logout.
3. Async draft arrives after initial useState; explicit hydration and conflict/error handling required. Six fields retain exact names.
4. Final submitDemo validates nonblank/theme but does not repeat HTML max lengths; storage reader validates types, not all bounds. Backend must enforce full rules.
5. Programmes and themes are conflated; add programme selection and pinned configuration. safeReturnPath hardcodes three theme codes.
6. IDs currently double as references; use UUID id and separate reference. No silent aliasing.
7. Timeline is linear; real status history may revisit stages. Version 1 is literal. Preserve display status, add stable statusCode.
8. Scores/reasons/decisions lack name properties; new explicit DTO fields above require review. HTML score strings become validated JSON numbers; criteria gain stable IDs.
9. Conflict checkbox resets on selection; server recusal must persist.
10. Reports use all raw ideas and partial page data would distort counts; use scoped aggregate APIs. Updates inferred from feedback become notifications.
11. Demo consent is not production privacy/IP consent. Admin/system pages have descriptions, not functioning configuration forms.
12. Recommendation phrases map explicitly to REQUEST_INFORMATION / RECOMMEND_APPROVAL / RECOMMEND_DECLINE; final decision codes/authority remain unresolved. Evaluation feedback does not imply publication.

Existing roles: submitter, evaluator, adjudicator, administrator, management, system-administrator. Existing themes: digital, sustainable, inclusive. Status fixtures: Submitted, Under review, Feedback, Approved, Award. Four criteria: Problem & relevance; Originality; Feasibility; Potential impact. None of these fixtures establishes final CEDA policy.
